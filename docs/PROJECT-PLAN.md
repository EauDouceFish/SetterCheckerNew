# SetterCheckerNew 立项与总体设计

状态：已确认，2026-09-03

## 一、这个工具要解决什么问题

帧同步日志会记录函数的进入和退出。记录太多会增加日志量，所以不会修改战斗数据的函数可以加上 `[NoLogTrack]`，不再记录。

SetterCheckerNew 要回答三个问题：

1. 哪些函数会修改战斗数据，必须保留日志？
2. 哪些函数不会修改战斗数据，可以添加 `[NoLogTrack]`？
3. 代码上的现有标签和实际函数行为有哪些不同？

最终结果不是自动修改代码，而是生成一份清楚的检查报告和修改预览，由开发者决定是否修改。

## 二、判断标准

以下函数必须保留日志：

- 修改当前对象中的数据。
- 修改传入对象中的数据。
- 修改全局或静态数据。
- 修改集合、数组、事件或通过 `ref/out` 传入的数据。
- 调用了另一个必须保留日志的函数。
- 创建了一个 khengine 业务对象，并把它返回、保存、注册或交给外部继续使用。
- 代码上明确标了 `[LogTrack]`。

以下函数可以免除日志：

- 所有会执行到的函数都已检查清楚。
- 没有修改任何函数外部仍然存在的数据。
- 即使创建了临时对象，也只在函数内部使用，函数结束后不再存在。

不能确定时，不允许猜成其中一种。工具必须指出具体卡在哪个函数、哪个调用位置、缺少什么信息，并结束本次正式检查。

## 三、现有 NoLogTrack 怎么处理

项目中已有的 `[NoLogTrack]` 先视为可信的人工决定。

具体规则如下：

- 类上有 `[NoLogTrack]`：这个类中原本会记录日志的函数全部继续免除日志，并在报告中标记为 `NLTClass`。
- 方法上有 `[NoLogTrack(Reason)]`：这个函数继续免除日志。
- 方法上只有裸 `[NoLogTrack]`：这个函数也继续免除日志。

不过，工具仍会单独检查这些函数的真实行为：

- 如果带 Reason 的方法或整个类实际会修改数据，只放进“可信豁免复查”清单，不报警。
- 如果裸 `[NoLogTrack]` 实际不会修改数据，不报警。
- 如果裸 `[NoLogTrack]` 实际会修改数据，报警“缺少 Reason”。
- 所有可能调用到这个裸标签函数的上层函数也进入同一告警清单。
- 每个受影响函数只列一次，并给出一条最短的调用过程，避免报告重复膨胀。

现有标签只影响最终是否记录日志，不会阻止工具检查函数内部真实做了什么。

## 四、整个工作分成哪几部分

整个工具只分成七个工作部分。每一部分都有明确输入和输出，后一部分只能使用前一部分已经整理好的结果。

### 第一部分：把需要检查的材料找齐

输入：`D:/KiHan/khengine.runtime.csproj`。

这部分做四件事：

1. 使用这个项目当前真正采用的编译设置读取代码。
2. 找出 khengine 自己的源码。
3. 找出它依赖的其他源码项目和编译后的 C# 程序文件。
4. 如果遇到只有函数声明、没有真实函数内容的参考文件，找到当前运行环境对应的真实文件。

输出是一份“本次检查到底使用了哪些源码和编译文件”的材料清单。

只有 khengine 自己的函数进入最终统计。依赖项目和外部文件只是为了看懂 khengine 调用了什么，不要求它们修改标签。

如果同一个外部文件找到多个不同版本，或者找不到真实实现，这一部分直接停止，不随便挑选。

### 第二部分：列出所有函数和现有标签

这部分先把所有可能用到的函数列成一张表，记录：

- 函数属于哪个类。
- 函数名称和参数。
- 函数在哪个文件、哪一行。
- 它有没有 `[NoLogTrack]`、Reason、类级标签或 `[LogTrack]`。
- 它是否进入最终统计。

进入最终统计的是：

- 普通命名函数。
- 运算符函数和类型转换函数。
- 属性的写入部分。
- 自定义事件的添加和移除部分。

只帮助分析、不进入最终统计的是：

- 构造函数。
- C# 属性的读取部分，因为现有日志工具本来就不会记录它。
- 接口和没有函数内容的抽象声明。
- 函数内部的小函数、匿名函数和编译器自动生成的函数。
- 现有日志工具明确跳过的 `getInstance` 和 `BaseProxy_*`。

这一步的输出是唯一的函数总表。之后所有结果都使用这张表中的身份，不靠函数短名称互相匹配。

### 第三部分：看懂每个函数自己做了什么

源码函数使用 C# 编译器提供的代码理解能力读取。编译后的 C# 程序文件直接读取其中保存的真实函数指令。

两种来源都只记录相同的几类事实：

- 写了谁的数据。
- 调用了哪些函数。
- 创建了什么对象。
- 新对象有没有被返回、保存或交给其他对象。
- 传入的对象、当前对象和新对象之间是什么关系。

这一部分不决定 Getter、Setter、NoLogTrack 或 ShouldTrack，只记录函数真实做过的事情。

例如，下面几种写法最后都记录为“修改传入对象”：

```csharp
actor.Hp = 10;
actor.SetHp(10);
list.Add(actor);
fieldInfo.SetValue(actor, 10);
```

它们进入同一套后续判断，不各写一套结论。

### 第四部分：找出每一次调用实际可能进入哪些函数

普通调用只有一个明确目标，可以直接连接。

下面四种写法可能有多个目标：

1. 调用接口：实际对象可能来自不同实现类。
2. 调用可重写函数：运行时可能进入某个子类重写的函数。
3. 调用保存到变量里的函数：这个变量可能绑定过多个函数。
4. 反射调用：根据对象类型和字符串寻找字段、属性或函数。

这四种情况遵守同一条规则：

> 找出当前代码和函数输入允许的全部目标。只有全部目标都不会修改数据，这次调用才算不会修改数据。

反射处理方式如下：

- 读取字段：只是读取。
- 读取属性：继续检查属性的读取函数。
- 写字段：记录对实际字段的写入。
- 写属性：继续检查实际属性写入函数。
- 调用函数：继续检查所有名称和参数都匹配的实际函数。
- 按类型创建对象：继续检查实际构造函数，并判断新对象是否被交给外部。

如果代码明确写了 `GetMethod("Foo")`，只查找符合条件的 `Foo`。

如果函数允许外部传入任意名称，就检查当前代码范围内所有确实能够匹配的名称。这与“接口的任意一个实现会修改数据，就必须保留日志”完全相同，不是遇到未知就直接判为 Setter。

第一版不读取 LogicData。SetterCheckerNew 检查的是函数本身具备什么能力，不模拟当前某一批游戏数据恰好传了哪些字符串。

### 第五部分：从最底层向上汇总结果

先找出直接修改数据的函数，再看谁调用了它们：

```text
C 直接修改战斗数据
B 调用了 C，所以 B 也会修改战斗数据
A 调用了 B，所以 A 也会修改战斗数据
```

每发现一个函数结果发生变化，就只重新检查调用它的上层函数。一直重复，直到所有结果都不再变化。

这样可以正确处理：

- 多层嵌套调用。
- 两个函数互相调用。
- 接口、重写、委托和反射产生的多个目标。
- 修改函数内部新对象，但新对象没有离开函数的情况。
- 新对象被返回、保存或注册，从而需要保留日志的情况。

这一步先完全不考虑现有 `[NoLogTrack]`，得到每个函数真实行为的检查结果。

### 第六部分：应用现有标签规则

这部分把第三节的可信标签规则应用到真实行为结果上：

- 生成最终应该记录或免除日志的结果。
- 生成可信豁免复查清单。
- 找出裸 `[NoLogTrack]` 中实际会修改数据的函数。
- 找出所有会调用到这些函数的上层函数，并生成“缺少 Reason”告警。
- 找出没有 NLT、实际又不会修改数据的函数，作为补标建议。

标签处理只发生在这里。前面读取代码、寻找目标和汇总调用时，不允许偷偷忽略带标签的函数。

### 第七部分：生成报告

同一份检查结果生成一份文本报告和一份 JSON 报告，内容必须一致。

报告包含：

- khengine 函数总数。
- 工具判断可以 NoLogTrack 的数量与源码现有数量。
- 工具判断 ShouldTrack 的数量与源码现有数量。
- 源码有 NLT、但实际会修改数据的可信豁免复查。
- 裸 NLT Setter 和受影响的上层调用过程。
- 源码没有 NLT、但可以补标的函数。
- 明确的标签冲突。
- 找不到函数内容或无法完成判断的具体位置。
- 每个步骤花费的时间。
- 建议标签修改的代码预览，但不修改 KiHan。

报告按固定顺序输出，保证相同代码重复运行得到相同结果。

## 五、代码怎样分开，才不会重新变乱

整个仓库只建立三个项目：

1. 核心项目：完成上述七部分工作。
2. 命令行项目：接收项目路径和报告目录，然后启动核心项目。
3. 测试项目：放置小型测试代码和 khengine 写法复刻代码。

核心项目内部也按上述七部分放置代码。每一部分只能负责自己的产物：

- 找材料的代码不能判断 Setter。
- 读取函数内容的代码不能处理 NLT。
- 寻找实际调用目标的代码不能直接返回 ShouldTrack。
- 汇总结果的代码不能自己读取源码或外部文件。
- 报告代码不能重新计算函数结果。

真正需要两种实现的地方只有两个：

- 读取源码函数和读取编译后函数，最终必须交出同样格式的函数事实。
- 文本报告和 JSON 报告，最终必须使用同一份检查结果。

其他部分先使用直接、普通的类，不为了“将来可能变化”提前建立空接口、插件系统或依赖注入框架。

这个拆分符合以下简单原则：

- 每部分只做一件事。
- 某一部分变化时，尽量不改其他部分。
- 源码读取和编译文件读取可以互相替换，结论不能变化。
- 上层只依赖已经整理好的结果，不依赖底层使用了哪种技术。

## 六、绝对禁止单个函数特判

禁止出现下面这种代码：

```csharp
if (functionName == "某个业务函数")
{
    return ShouldTrack;
}
```

也禁止通过配置文件把某个外部函数直接写成 Getter 或 Setter。

必须处理的是一整类行为：

- 字段写入是一类行为。
- 属性写入是一类行为。
- 根据类型和名称调用函数是一类行为。
- 创建对象是一类行为。
- 调用保存到变量里的函数是一类行为。

例如 `FieldInfo.SetValue` 不能直接标成 ShouldTrack，而是要找到它代表的实际字段，然后产生一条普通字段写入记录。最终是否 ShouldTrack 仍然由统一汇总步骤决定。

项目里的 `ReflectUtil`、KFL 包装函数和其他工具函数不做专门适配。工具会继续读取它们的源码或编译后内容，直到自然进入上述通用行为。

以后增加新处理时，也必须满足：

- 解决一整类写法，不只解决报告里的一个函数。
- 只补充“代码实际做了什么”，不能直接补 Getter/Setter 结论。
- 同时增加这一类写法的正常测试和边界测试。

## 七、边界情况怎么处理

| 情况 | 第一版处理方式 |
|---|---|
| khengine 源码函数 | 直接读取源码 |
| 有真实内容的外部 C# 程序文件 | 读取文件中的函数指令 |
| 只有声明的参考文件 | 找到当前运行环境真实文件后再读取 |
| 接口和可重写函数 | 预先找出全部实现和重写函数 |
| 委托和事件回调 | 跟踪这个函数变量可能绑定的全部目标 |
| 反射读取、写入和调用 | 根据类型、名称和参数找出全部合法成员 |
| 动态创建对象 | 找到真实类型与构造函数，再判断对象是否被交给外部 |
| 函数内部小函数和匿名函数 | 参与判断，但不进入最终标签统计 |
| 构造函数和属性读取函数 | 参与判断，但现有日志工具不记录，所以不进入最终统计 |
| 运行时临时生成新代码 | 停止并明确报告，不能猜 |
| 运行时再加载未知程序文件 | 停止并明确报告，要求先确定文件范围 |
| 原生代码调用 | 第一版记录为已延期问题，不读取原生函数体 |
| LogicData 等游戏内容 | 第一版不用于限制函数可能输入 |
| 其他条件编译组合 | 第一版只使用当前项目采用的组合 |

除已经确认延期的原生代码外，只要当前 khengine 触发一个无法处理的边界，对应阶段就不能宣布完成。

## 八、怎样保证速度

第一版不做硬盘缓存。工具像 CMake 的 `-j4` 一样，由运行参数决定同时安排多少份工作：

```text
SetterChecker analyze --project D:/KiHan/khengine.runtime.csproj --output <报告目录> -j4
```

下面三种写法含义相同：

```text
-j4
-j 4
--jobs 4
```

`-j4` 表示建立 4 个工作名额。只要任务之间互不依赖，就可以同时处理 4 份工作。用户也可以使用 `-j1`、`-j2`、`-j8` 或其他正整数；代码里不把 4 写死。不填写时默认使用 4。

整个检查过程共用同一个工作数量，不允许每个步骤私自再创建一批线程。例如设置 `-j4` 后，工具内部始终按照这 4 个工作名额安排任务，不会在读取源码时开 4 份、读取外部文件时又额外开 4 份，最后失去控制。

以下工作可以拆开同时执行：

- 不同源码文件的读取。
- 不同外部编译文件的读取。
- 不同函数自身行为的检查。
- 不同接口、重写、委托和反射调用的目标查找。
- 不同报告项目的内容准备。

以下工作存在明确先后关系，不强行同时执行：

- 材料没有找齐前，不能开始读取函数内容。
- 函数清单没有完成前，不能查找全部实际调用目标。
- 实际调用目标没有找齐前，不能生成最终结论。
- 最终结论没有完成前，不能写正式报告。

在每一个可同时执行的步骤中，具体做法都是：

1. 把待处理的文件、函数或调用放进同一个任务队列。
2. 按 `-j` 指定的数量启动工作线程。
3. 每个线程处理完一项后继续领取下一项，直到队列为空。
4. 某一项失败时停止分发新任务，收集已经发生的错误并正常结束其他线程。
5. 所有线程完成后，按固定顺序合并结果，再进入下一步骤。

因此 `-j4` 不表示每一秒都必须有 4 个线程忙碌；当某一步只有两项工作时，只能同时处理两项。它表示只要有足够多的独立任务，就让 4 个工作线程共同处理，与 CMake `-j4` 的使用方式一致。

其他一次运行内的基础提速包括：

- 每个源码文件只读取一次。
- 每个编译后文件只打开一次。
- 函数、类型、实现关系和“谁调用谁”都放进快速查找表。
- 某个函数结果变化时，只重新检查调用它的函数，不重新扫描全部代码。
- 反射查找先按类型、名称和参数筛选，不对每次调用遍历所有函数。
- 每个步骤单独计时，慢在哪里能够直接看到。

正式验收分别记录：

1. 编译 SetterCheckerNew 花费的时间。
2. 已经编译好的工具完整检查 khengine 花费的时间。
3. 从编译工具到生成报告的总时间。

最好在 5 秒内完成完整检查；包含工具编译时，10 秒是最低可接受目标。未达到时先优化实际最慢步骤，不通过新增缓存掩盖问题。

正式性能验收至少使用相同代码分别运行：

```text
-j1
-j2
-j4
```

每种工作数量至少运行三次，记录首次时间和中间一次的时间，并计算 `-j4` 相比 `-j1` 的实际加速。机器条件允许时再增加 `-j8`。

不同工作数量生成的两份报告必须逐字一致。并行只允许改变耗时，不允许改变函数结论、证据、数量或输出顺序。

## 九、怎样测试

### 1. 每增加一种能力，先写一个会失败的小例子

例如准备下面两个函数：

```csharp
public void SetHp(Actor actor)
{
    actor.Hp = 10;
}

public int GetHp(Actor actor)
{
    return actor.Hp;
}
```

先确认工具还不能正确区分它们，再写最少代码让这个例子通过。一个例子通过后，再增加下一种写法。

测试只检查开发者真正关心的结果：

- 最终是 Getter 还是 Setter。
- 为什么得到这个结果。
- 实际找到了哪些被调用函数。
- 有没有正确处理现有标签。

测试不检查某个内部类调用了几次，也不依赖内部代码怎样拆分。

还要单独验证工作数量参数：

- `-j1`、`-j2`、`-j4` 和 `-j8` 都能完成同一份检查。
- 不同工作数量得到完全相同的结果和报告顺序。
- 0、负数、非数字和缺少数值时给出清楚错误。
- 某个并行任务失败时，其他线程能够正常结束，工具不会卡死。

### 2. 同一段代码同时检查源码和编译后文件

测试代码先直接按源码检查，再编译成程序文件重新检查。

两次得到的修改行为、调用目标和最终结论必须相同。这样可以防止源码和外部文件形成两套互相矛盾的规则。

### 3. 复刻 khengine 的每一种真实写法

在一个阶段达到完成度时，只读扫描 khengine，整理这个阶段实际出现的每一种写法。

每一种写法都在测试区建立一个尽量小、但关键结构与原代码相同的例子，并记录它对应的真实函数。

例如：

- 普通字段赋值出现很多次，只需要一个代表例子。
- 字段、属性、集合、`ref/out`、接口、重写、委托和反射分别需要代表例子。
- 同一种语法如果对象来源不同、最终效果不同，也要分成不同例子。

然后同时检查真实函数和测试例子，对比：

- 最终结论是否相同。
- 修改的是哪一类对象是否相同。
- 找到的调用目标是否完整。
- 上层传播结果是否相同。

两边不同，这个阶段不能通过。

### 4. 标签不同不能自动判谁对谁错

完整检查 khengine 后，如果源码标签与工具结论不同，由 AI 阅读真实代码和完整调用过程，分成以下情况：

- 工具判断错误：修复工具并增加测试。
- 裸 NLT Setter：可信豁免，但告警缺少 Reason。
- 带 Reason 或类级 NLT Setter：保留在可信豁免复查中。
- 没有 NLT 的 Getter：列为可以补标。
- 确实需要业务决定：写清楚为什么当前通过或不通过，不能只给一个结果。

## 十、开发顺序

每一阶段开始前，只详细设计当前阶段；当前阶段测试通过、真实代码验收完成并提交后，才设计下一阶段。

### 阶段一：最简单的源码检查

读取一个很小的 C# 测试项目，识别普通函数、直接字段写入和纯读取，并输出最小结果。这一步先跑通从项目输入到函数结论的完整过程。

### 阶段二：现有标签和多层调用

加入普通函数互调、循环调用、三种 NLT、`NLTClass`、裸 NLT Setter 告警和上层函数告警。

### 阶段三：完整源码写法

加入属性、集合、事件、`ref/out`、新对象、对象逃逸、内部函数、匿名函数和当前 khengine 出现的其他直接写法。

### 阶段四：接口和可重写函数

提前建立全部实现关系，只有全部实现都是 Getter 才允许免除日志。

### 阶段五：委托和事件回调

找出函数变量的全部来源和绑定目标，再按普通调用传播。

### 阶段六：外部编译文件

读取真实函数指令、处理参考文件与真实文件的映射，并让同一段测试代码的源码检查和编译后检查得到相同结果。

### 阶段七：反射和动态创建

统一处理字段读取、字段写入、属性、函数调用和创建对象，不增加 KFL 或业务函数专用规则。

### 阶段八：完整报告与 khengine 验收

生成文本和 JSON，复刻 khengine 的每一种实际写法，逐项审计标签差异，并完成时间测试。

每一阶段都必须：

- 先写当前阶段的具体设计和测试例子。
- 测试全部通过。
- 检查当前能够覆盖的 khengine 真实写法。
- 检查完整代码差异。
- 提交并推送一个可运行版本。
