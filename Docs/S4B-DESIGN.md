# S4b 设计与测量

> 分支 `s4b-prototype`（基于 `9e9e077`，即 S4a 之前）。编写日期 2026-09-28。
> 本文只交设计与实测，不申请合并原型代码。所有数字均为 khengine 实测，测量方法见第 1 章。

---

## 0 结论（先读这一节）

**不建议按 5.5 节原方案施工**（分批闭包，同时删除按需调度与需求登记）。建议改做一个范围小得多的替代方案：**推测并行解析 + 按原顺序提交**。它保留现有的需求登记，只把 `ResolveCall` 放到多线程上。

理由：

1. **5.5 节的"总耗时 ≤ 7 秒"不可达，与是否做 S4b 无关。** 分析阶段以外的固定开销已经有 9–10 秒：材料 3.2–4.6 秒、函数总表 2.5–3.5 秒、标签与报告约 1 秒、进程启动约 1.5 秒。第 11 章的"速度 B ≤ 12 秒"也要求分析阶段 ≤ 约 2.5 秒，同样达不到。
2. **能并行的部分有限。** S4a 之后，调用解析（`ResolveCall` 及其分派、绑定）约占分析阶段的 40%，即 11 秒里约 4.4 秒。其余是函数体读取（已并行）、注册扫描、TOP 与摘要、调度，都不在 S4b 的并行范围内。
3. **分批会削弱剪枝，读取量风险已经测到。** 在原型里，只要让剪枝信息晚一个波次到达，就多出 29,172 次调用解析。这些解析的目标里有 13,072 个函数，现在根本不需要读函数体，相当于读取量 +40%，而且还没算这些函数继续展开的连锁读取。
4. **任何改变执行顺序的方案都会暴露三处隐藏的顺序依赖**（见 5.4 节）。其中一处是真缺陷：同一个源码函数，提取出的函数体随目录缓存的填充顺序不同（13 个值对 10 个值）。无论做不做 S4b，都应该先修。
5. **删行很少。** 5.5 节删除清单约 550 行，但分批调度加上值流求解要新增 300–500 行，净减 0–300 行。离 3.5 节的 9,500 行差很远，也不足以抵消其他增长。S4a 分支目前的 Core 已有 13,303 行，超过 13,000 行硬上限。

替代方案的原型（本分支，环境变量 `SC_S4B_WAVE=1` 开启）实测结果：

| 项目 | 顺序（现状） | 推测并行原型 |
|---|---:|---:|
| 主循环墙钟，中位数 / 最小值 | 18.5 / 13.8 秒 | 14.5 / 12.0 秒 |
| 分析阶段，中位数 / 最小值 | 19.9 / 15.0 秒 | 16.1 / 13.3 秒 |
| 函数体读取数 | 32,258 | 32,258（集合与顺序完全相同） |
| 15,304 个函数的 Actual、Decision、Failure、证据 | — | 全部一致 |
| 与基线 `report.json` 的差异 | 零 | 仅 `ExternalFunctions` 两条（原因已定位，见 5.4 节） |
| `-j4` 与 `-j8` | — | 逐字节一致 |

预计在 S4a 之上能省 1.5–3 秒，分析阶段约 9.5 秒降到 7–8 秒（安静机器）。主要风险是 5.4 节的顺序依赖必须先修干净。施工步骤见第 7 章。

### 2.2 阻碍并行的共享可变状态，以及原型的处理

| 状态 | 位置 | 问题 | 原型处理 |
|---|---|---|---|
| 调用结果 `m_results` | `SetResult`、`SetOutResult`、`StoreOrigin` | 解析过程中会写，而且**同一次解析会读回自己刚写的结果**（例如循环里的 `s = string.Format(.., s, ..)`） | 推测期间写入推测专用的覆盖表，自己能读到；提交时再真正写入 |
| 合成值编号 `m_nextStored` | `StoreOrigin` | 编号按分配先后产生，会进入目标身份字符串 | 推测期间若需要新编号，就判为无效并退回顺序解析（198 次） |
| 需求登记 `m_valueUsers`、`m_callUsers`、`m_neededCalls`、`m_pendingCalls`、`m_readers`、`m_changedReaders`、`m_requested*` 等 | `RequireBody`、`RequireCall`、`RequestMember`、`RequestIncoming`、`Observe` | 查询本身就在写需求图 | 推测期间只记下"读了哪些键"和去重后的副作用，提交时按原顺序重放 |
| 活跃缓存 `m_liveValues` | `HasValueReader` | **缓存结果与查询时机有关**。提前查询会改变之后的需求判断 | 推测前的查询记日志并撤销 |
| 函数序号 `m_functions` | `Include` | 序号按登记先后分配，会进入 `TargetIdentity` 和目标排序 | 推测期间不登记，提交时按原顺序重放 |
| 反射查询缓存 `ReflectionQueries` | `ReadReflection` | 解析时写 | 推测期间延后写入 |
| 局部缓存 `m_reaching`、`m_convertedTypes`、`m_runtimeTypes` | 来源回溯、类型收窄 | 纯缓存，但不是线程安全字典 | 改为 `ConcurrentDictionary` |
| 分派缓存 `DispatchIndex` | `Ranges` 里的 `TargetCandidates` 是**多个调用共享的惰性枚举器** | 非线程安全 | 改为 `ConcurrentDictionary`，枚举器推进时加锁 |
| 目录缓存 `m_sourceInterfaceMaps`、`m_sourceOverrides`、`m_relationDefinitions` | `MethodCatalog` | 普通 `Dictionary` | 加锁 |
| 目录惰性装载与 Cecil 模块锁 | `m_loadedTypeLock`、`lock (module)` | 线程安全，但分派首次计算会在这里串行 | 未处理，这是第一波次慢的主因 |
| `TopTracker` | `stopAfterTarget` 在解析中途 `Bind` | 解析时会改剪枝状态 | 推测期间用只读的 `WouldBecomeTop` 预测；提交时先用只读预测核对全部停止点，再真正绑定并复核 |
| `RegistrationIndex` | `m_symbols`、`m_boundLocations`、惰性位置枚举 | 非线程安全 | 不在 `ResolveCall` 路径上，仍留在主线程 |
| Roslyn 语义模型 | `ReadSourceModel` | 查询本身线程安全，模型缓存已是并发字典 | 无需处理 |
| `AnalysisTiming` | `m_current` 单线程切换 | 多线程会写乱 | 工作线程上不计时 |
| 报告字段 `OriginCalculations` | `OriginReadCount++` | 它是工作量计数，却参与确定性比较 | 推测期间单独计数，提交时累加；最终与基线**完全相同**（373,528） |

## 3 问题 2：分批闭包的具体结构

下面给出如果要做 5.5 节方案应该怎么做，以及为什么必须保留一部分需求机制。

### 3.1 每一批的步骤

第 k 批：

1. **读取**：候选是上一批合并后登记为"需要函数体"的函数。读取前要**再核对一次活跃性**：请求者已成为 TOP 或已不活跃的请求直接丢掉。这一步是控制读取量的关键（见第 0 章第 3 条）。候选按 `MethodId` 排序后并行读取，然后在主线程顺序执行 `ReadBody` 和 `TopTracker.ReadDirect`。
2. **值流**：见 3.2 节。
3. **解析**：工作集是活跃函数中尚未解析的调用，加上输入发生变化的调用。每个工作项并行解析，返回五样东西：
   - `ResolvedCall`
   - 副作用清单（结果写入、需要的函数体、需要的调用结果、字段与来向请求、新登记的函数）
   - 读取键集合
   - 每个目标的剪枝判断
   - 失败文本
4. **合并**：按 (`MethodId`, `BlockId`, `Order`) 的 Ordinal 顺序合并。函数序号、合成值编号都在这里按顺序分配。`Connect`、`TopTracker.Bind`、需求登记也在这里按同一顺序执行。
5. **剪枝传播**：`TopTracker.Propagate` 和 `Settled` 在批次边界一次完成，更新活跃集合，规则与现在的 `ActivateBehavior`、`Settled` 相同。
6. **注册**：本批新增的注册请求按名字排序，在主线程推进，结果进入下一批。
7. **终止**：没有新函数体、没有变化的调用、也没有注册请求时停止。

批次数估计：只沿调用边，从根到最深的函数体有 13 层（各层函数体数：15,512 / 8,198 / 2,613 / 1,757 / 2,470 / 674 / 295 / 184 / 166 / 112 / 45 / 25 / 9 / 1）。另有 197 个函数体来自值需求或注册扫描。再加上值流收敛要 3 批（见 5.2 节），所以**至少 14–17 批**。现状是 1,237 次读取批次。

### 3.2 值流的节点、边与抽象对象

- **节点**：`(函数序号, 值编号)`。khengine 上有 767,645 个函数体值，外加解析时产生的合成值（最终 1,531 个）和 `out` 结果值。
- **抽象对象**按分配位置区分：
  - `NewObject`、`NewArray`、`Iterator`、`ShallowCopy`、`StackAllocation`，位置是 (函数, 值编号)。
  - `Function`（委托）是"函数加上绑定对象的节点"，两者分开保存，与现有 `BoundReceiver` 相同。
  - `Type`、常量。
  - **跨函数返回的新对象，在调用处重新编号为 `Fresh(调用结果值)`**，相当于一层堆克隆，与 4.4 节 `CallResult` 的换算一致。这样 `FactoryInstancesKeepSeparateCallbacks` 里两次 `Create` 得到的 holder 是两个对象，`first.Callback` 只会连到 `Pure`。
- **边**：
  - 局部边：`SlotRead` 按最近赋值（`ReadReachingValues`），`Merge`，`Conversion` 带类型收窄（`ConvertOrigin`），`ValueCopy`，`CapturedVariable` 按符号。
  - 调用边：每个 `ResolvedCallTarget` 上，实参到形参一条，返回值到调用结果一条，`out` 写回到 `out` 结果一条。返回边必须经过被调函数的"返回摘要"，按形参槽位代换成本次实参。这对应现有 `ReadTargets` 里 `item.Binding` 的一层调用点区分。去掉这一层，会把所有调用者的实参混在一起。
  - 字段边：对 `Fresh` 对象按 (对象, 字段) 区分；其余对象按 (声明类型, 字段名) 汇总，与现有 `m_writes` 一致。
  - 数组元素：按数组分配位置。
  - 注册边：来自 `RegistrationIndex` 找到的外围调用。
- **类型边界**：未知对象带声明类型，字段读、形参读都取声明类型作上界，转换不扩大范围。这保住了 `FieldKeepsReceiverTypeBoundary`：`holder.Proxy` 的声明类型是 `Proxy`，不会连到 `Unrelated.Read`。
- **求解**：集合只增不减。单线程工作表按节点序号推进，结果与处理顺序无关。

**关键限制**：值流需要哪些函数体，只能从活跃调用的接收对象、委托和反射实参反向推出。这本身就是现在的"值需求"。所以 5.5 节要删除的 `RequireBody`、`RequireCall`、`NeedsCall` 这一类登记，换成值流后仍然需要一个等价物，只是表达形式不同。能真正删掉的是逐调用的输入订阅（`Subscribe`、`Observe`、`Notify`、`CaptureInputs`、`SaveCallInputs`），代价是每批要重算整个值流。

### 3.3 调用如何并行

- 并行粒度是单个调用位置。同一函数内的调用不必串行，因为推测结果本来就要在提交时按顺序核对。
- 解析函数必须改成"读共享状态、返回副作用"：
  - `SetResult`、`Include`、需求登记都变成返回值。
  - 同一次解析内部读自己写的结果，必须能读到（2.2 节第一行）。
  - 剪枝回调改为只读判断。
- 分派缓存改为并发字典，把惰性枚举器换成"首次完整计算、之后只读"的数组，免得多个线程争同一个枚举器。

### 3.4 剪枝在批次间如何保持

- `TopTracker` 的状态只在合并阶段修改。批内解析用批开始时的快照，只读判断"绑定这个目标后调用者会不会成为 TOP"（原型里的 `WouldBecomeTop`）。
- 批内某个函数成为 TOP 之后，同一批里它其余调用的解析就浪费了。代价实测见 5.3 节：一个波次的滞后，有 31% 的推测没被用上。
- **必须在读取前重新核对活跃性**（3.1 节第 1 步），否则这些浪费的解析引入的 13,072 个新函数都会被读取，而且会继续展开。
- `IsLive`、`IsDecided` 的定义不变，只是求值时机统一放到批次边界。

### 3.5 `-j1`、`-j4`、`-j8` 逐字节一致的保证

1. 所有影响输出的写入（函数序号、合成值编号、结果、需求、TOP 绑定）都在合并阶段按固定键顺序执行。工作线程只读。
2. 工作线程读到的状态，全部来自批开始时的快照或只增的纯缓存。纯缓存包括分派结果、`m_reaching`、类型收窄。
3. 与查询时机有关的缓存（`m_liveValues`）只能在主线程、固定时点读取。
4. 修掉 5.4 节第 3 项：源码函数的符号来源必须与首次访问顺序无关。
5. `OriginCalculations` 只统计被采用的解析，或者移到 `OperationCounts`。
6. 原型已验证：推测并行版 `-j4` 与 `-j8` 的调用导出 0 行差异、报告逐字节一致。`-j1` 在最终原型上没有重测。

### 5.2 模拟：已知全部函数体时解析全部调用

冻结最终状态，对 69,944 个调用位置各解析一次。分派缓存是冷的，目录缓存是热的。S4a 前代码：

| 线程数 | 墙钟 |
|---|---:|
| `-j1` | 9.92 秒（首轮，含分派结果首次计算） |
| `-j4` | 2.48 秒 |
| `-j8` | 1.29 秒、1.09 秒（两次，结果逐项相同） |

与主循环最终结果相比：69,282 个一致，660 个不同，另有 2 个其余差异。

- 660 个不同的调用者都是 TOP。剪枝时机不同导致目标列表长短不同，不影响结论。
- 2 个其余差异的调用者既不活跃、也没有值需求，所以不影响任何结论：
  - `ILRuntime AppDomain.GetType`：原主循环保留了早期的"反射类型名称尚未确定"，没有再重算；在完整状态下重算会得到另一种失败。
  - `Environment.GetResourceString`：同样是早期结果没有重算。
- 这 2 处说明，现有增量失效在不活跃函数上会留下旧结果。

从空调用关系开始、全部函数体已知时的分批不动点（`-j8`，每批重解析全部位置）：

| 批次 | 解析 | 合并 | 调用变化 | 结果写入变化 |
|---|---:|---:|---:|---:|
| 1 | 1.58 秒 | 0.45 秒 | 69,944 | 7,731 |
| 2 | 1.89 秒 | 0.13 秒 | 871 | 2 |
| 3 | 1.38 秒 | 0.04 秒 | 35 | 1 |
| 4 | 1.04 秒 | 0.07 秒 | 0 | 0 |

- 合计 7.1 秒（含建表 0.49 秒）。如果只重解析有变化的调用，第 2–4 批的开销可以忽略，合计约 2.5 秒。
- 最终结果与主循环的差异，和冻结重解析的差异是同一批（2 条其余差异加上 TOP 调用者），说明**值流在完整函数体集合上 3 批收敛，结果与处理顺序无关**。
- 这项模拟**不包含发现函数体的过程**，等于假设剪枝完美，所以是分批方案的下限。

### 5.3 主循环内的推测并行原型

做法：把当前就绪队列当作一个波次，在冻结状态上并行解析其中的待处理调用。然后在顺序主循环走到每个调用时，核对推测结果是否仍然成立：

- 需求标志没有变；
- 读过的键在推测之后没有被 `Notify`；
- 剪枝停止点一致。

成立就重放副作用、直接采用；否则退回顺序解析。

| 项目 | 数值 |
|---|---:|
| 波次 | 6,001 |
| 其中并行波次（至少 8 个调用） | 343 |
| 推测解析 | 93,262 次 |
| 采用 | 63,822（68%） |
| 输入已变，退回 | 259 |
| 剪枝停止点不同，退回 | 9 |
| 需要新合成值，退回 | 198 |
| **未被使用（函数先成了 TOP 或不再活跃）** | **29,172** |
| 未使用推测的目标函数 | 28,462 个，其中 **13,072 个在顺序运行中从未读取函数体** |
| 推测并行阶段墙钟 | 5.4–8.0 秒 |
| 其中第一波次 | 60,070 个调用，3.48 秒 |
| 提交阶段剩余的顺序 `ResolveCall` | 1.1–2.1 秒（顺序版 9.2–13.1 秒） |
| 分配 | 7.2 → 11.0 GB |
| GC 暂停 | 1.5 → 2.1–2.4 秒 |

效率不如 5.2 节模拟的原因：

1. 31% 的推测没被用上。
2. 第一波次冷启动，分派结果首次计算集中在目录模块锁上。
3. 小波次多，负载不均。
4. 记录读取键与副作用有额外分配。

改进空间：只推测更可能被用上的调用；按函数分组，并行之前先完成 TOP 预测；分派缓存预热后再并行。

### 5.4 与现有结果的差异，以及发现的三处顺序依赖

原型最终结果：

- `Methods` 全部 15,304 个函数的 Actual、Decision、Failure、证据链与基线逐字节一致。
- `OriginCalculations` 一致。
- 唯一差异在 `ExternalFunctions` 两条：`KH.EventDispatcherImpl.addEventListener`、`removeEventListener`。

逐步对分定位过程中发现：

1. **同一次解析会读自己的写入。** `string.Format` 这类转换规则先 `SetResult` 自身结果，随后 `ReadFormattedArguments` 通过循环回边读到这个结果。一开始把写入延后，导致 `SavePlayerBuffWhenDead` 的格式化调用从 500 个 `ToString` 目标变成 0 个，证据链也变了。加了推测内覆盖表后消除。**任何把解析改成"只读快照 + 延后写入"的方案都必须处理这一点。**
2. **活跃缓存 `m_liveValues` 与查询时机有关。** 在推测前额外调用 `NeedsValues`、`NeedsCall`，会改变之后的需求判断。撤销日志消除了影响。这说明现在的结果依赖"哪一时刻问过哪个问题"，属于脆弱设计。
3. **源码函数的函数体提取与目录缓存的填充顺序有关（真缺陷，未修）。** `KH.KHEventDispatcher.addEventListener`（`kihan.common.runtime` 源码）：
   - 顺序运行提取到 13 个值：三个形参被当作 `CapturedVariable`（按名字 `eventType`、`listener`、`priority`）再 `SlotRead`，调用位置是 `@0:13`。
   - 推测运行提取到 10 个值：直接 `SlotRead` 形参，调用位置是 `@0:10`。
   - 两次运行读取它的批次（第 72 批）和时点（第 56,819 次解析后）都相同，差别只在之前谁先触发了目录里这个函数的源码符号。
   - 形参被当成"捕获变量"，说明提取时用的方法符号与形参所属符号不是同一个实例。推测是经不同 `CompilationReference` 得到的重定向符号。
   - 这会改变调用位置编号，进而改变 TOP 调用者的剪枝位置，最终体现为 `ExternalFunctions` 两条差异。
   - 现在的顺序实现碰巧每次顺序相同才没暴露。**S4b 或替代方案施工前都必须先修**：源码函数只能取所属编译的原始符号。

## 6 问题 5：风险与继续条件

### 6.1 5.5 节的继续条件逐条对照

| 条件 | 判断 |
|---|---|
| 总耗时 ≤ 7 秒 | **达不到**。非分析部分已有 9–10 秒 |
| 结果与现有零差异，或每条差异有解释 | 替代方案原型只差 2 条，已解释，修掉 5.4 节第 3 项后预期零差异。分批方案有 13,072 个额外读取的风险，没有原型能证明零差异 |

如果把条件理解为"**分析阶段** ≤ 7 秒"：

- 分批方案的理论下限：读取 1.5–2 秒、解析 1–2 秒、注册 1.2 秒、TOP 与摘要 1.5 秒、合并调度 0.5–1 秒，合计 6–8 秒。能否做到取决于读取量，而读取量未测。
- 替代方案预计 7–8 秒。

### 6.2 分批方案的主要风险

1. 滞后剪枝导致读取量上升。一个波次滞后就多出 13,072 个候选函数体；如果不在读取前重核活跃性，会连锁放大。历史上只按 TOP 剪枝时，耗时超过 440 秒。
2. 删除逐调用订阅后，每批要重算值流。值流节点约 77 万，至少 14–17 批，需要增量求解，否则单是值流就会数秒。
3. 精度：返回边必须保留一层调用点区分和一层堆克隆，否则 `FactoryInstancesKeepSeparateCallbacks` 这类测试会退化，第一类误差上升。
4. 死循环：本方案靠集合单调保证终止。所有"替换结果"的写入（现在的 `SetResult` 是覆盖写）都要改成只增，或者给出收敛论证。
5. 工作量大（第 7 章），而且与 S4a 冲突大，要等 S4a 合并后重做。

### 6.3 替代方案的主要风险

1. 推测正确性依赖"读过的键覆盖全部输入"。原型已经找到两处例外（5.4 节第 1、2 项）并处理。生产版需要把 `ResolveCall` 的全部副作用显式化，不能再靠线程静态拦截。
2. 收益受分派首次计算的锁竞争限制，在 S4a 之上的实际收益要重测。
3. 行数增加约 200–250 行，要与行数上限一起评审。

## 7 建议的施工步骤与工作量

按顺序进行，每步都要求与上一步零差异：

1. **修源码符号来源的顺序依赖（5.4 节第 3 项）。**
   - 做法：源码 `MethodEntry.SourceSymbol` 固定取所属编译的原始定义；加测试，验证同一函数经不同引用路径访问时提取结果相同。
   - 这一步与 S4b 无关，也应单独做。
   - 约 1 天。
2. **把 `ResolveCall` 改成显式上下文。**
   - 做法：引入 `ResolveContext`，收集结果写入、函数登记、需求登记、反射缓存写入，并提供"读自己写入"的覆盖表；顺序路径下立即应用。
   - 纯重构，零差异。
   - 约 1.5–2 天。
3. **推测并行解析加按原顺序提交。**
   - 做法：以就绪队列为波次；推测前的需求查询不能写缓存；提交时核对键、需求标志和剪枝停止点；分派缓存改为并发字典加只读结果数组；目录剩余的非线程安全缓存加锁。
   - 验收：`-j1`、`-j4`、`-j8` 逐字节一致，且与 S4a 零差异。
   - 约 2–3 天。
4. **减少浪费。**
   - 做法：已预测会成为 TOP 的函数，只推测到第一个 TOP 目标；第一波次先预热分派结果。
   - 目标：推测采用率从 68% 提到 85% 以上。
   - 约 1 天。
5. **（可独立做）合并函数体读取的小批次。**
   - 现在 1,237 批里有 1,100 批不超过 8 个函数。
   - 这项收益未测，要先单独测。
   - 约 0.5 天。

- **替代方案合计约 6–8 个工作日**，预计分析阶段在 S4a 之上再省 1.5–3 秒。
- **5.5 节原方案**（分批闭包、值流求解、删除订阅机制）估计 3–4 周。它要在第 1–2 步之后才能开工，风险见 6.2 节。收益上限与替代方案相近（多省 0–1.5 秒），**不建议做**。
