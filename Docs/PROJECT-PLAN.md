# SetterCheckerNew 设计与进度

## 一、最终目标

SetterCheckerNew 只服务于 `D:/KiHan/Packages/khengine`。

它读取 khengine 当前真正使用的 Unity 编译参数，检查所有相关源码和编译后的 C# 文件，最后回答：

1. 哪些可报告函数的真实行为是 Setter。
2. 哪些可报告函数的真实行为是 Getter。
3. 分析结论与源码现有标签有哪些差异。
4. 哪些人工豁免需要复查，哪些裸 `[NoLogTrack]` Setter 缺少 Reason。

工具生成文本报告、内容一致的 JSON 报告和标签修改预览，不自动修改 KiHan。

## 二、已经确认的判断规则

真实行为只分 Getter 与 Setter。以下行为属于 Setter：

- 修改当前对象、传入对象、对象图、静态数据、集合、数组、事件或 `ref/out` 数据。
- 调用函数后实际修改了调用者已有的对象、参数或静态数据；记录被调函数修改的是接收对象还是第几个参数，再映射回调用者，不能无条件复制被调函数的 Setter 结论。
- 创建 khengine 业务对象并将它返回、保存、注册或传给外部。

只修改函数内部创建且没有离开函数的临时对象，不属于 Setter。

普通根函数从符合初始化约定的状态开始：私有静态只读字段保留已证明的初始化值；不假设另一个独立入口在此前通过反射暗中破坏了这个约定。这是本次验收的输入边界，不是从“没有搜索到字段名”推导出的事实。主 Agent 依据 khengine 当前可见用途自主确定：具体反射写入主要操作业务数据；另有通用入口允许任意成员，所以不能声称这种能力不存在。

当前根函数中实际可达的普通写入、反射写入及未知可写调用仍照常处理，并覆盖初始化事实；不得忽略。数组初始化只用于证明长度等数值，不改变其属于共享静态对象的事实。初始化含未证明调用、重入、外部读取或异常路径时不给出初值证明；未闭合的反射写入也不能据此判成 Getter。

只有函数自身没有外部修改，并且全部合法调用目标的实际影响都闭合、没有造成外部修改，函数才是 Getter。不能闭合时保留准确失败证据，不为该函数给出最终结论；该轮验收失败，但报告仍应列出已证明项目和剩余问题。禁止猜测、保守判定或把部分结果当成全量结论。

`ShouldTrack`、`NoLogTrack` 和 `NLTClass` 是第六模块结合真实行为与源码标签后得出的最终日志决定，不是函数真实行为的别名。`[LogTrack]` 只强制最终决定为 `ShouldTrack`，不能把真实 Getter 改写成 Setter。

## 三、现有标签规则

- 方法级 `[NoLogTrack(Reason)]`、裸 `[NoLogTrack]` 和类级 `[NoLogTrack]` 都先作为可信人工豁免，最终不追踪。
- 豁免函数内部的写入不再使上层需要追踪；若上层还直接修改数据、调用其它未豁免函数，仍独立判断。比如 `A → B → C` 中 B 有可信 NLT，C 的写入在 B 处停止影响 A 的追踪决定，但 C 单独分析仍是 Setter。
- 工具仍独立检查所有豁免函数的真实行为。
- 标签不改变真实参数、字段写回、返回对象身份和能否正常返回。A 返回 NLT 工厂创建的业务对象，是 A 自己的对外返回，仍需追踪；丢弃结果或仅修改内部新对象不增加追踪。A 修改工厂返回的已有对象或将结果保存到已有对象，仍需追踪。
- 类级豁免下的可报告函数标记为 `NLTClass`。
- 带 Reason 的 Setter 和类级豁免 Setter 进入“可信豁免复查”，不报警。
- 只有裸 `[NoLogTrack]` 被独立分析为 Setter 时，告警“缺少 Reason”。
- 是否有 Reason 读取当前标签构造函数真正收到的原因字符串；不能用“括号里有参数”代替。当前 khengine 还存在只有 `NoLogTrackFlag` 数值的写法，它没有提供 Reason。
- 该告警传到所有能调用它的上层可报告函数；每个函数只列一次最短调用过程。
- 没有 NLT 或强制 LogTrack、且标签生效后没有剩余追踪影响的函数进入补标建议；其真实行为可能是 Getter，也可能仅因调用可信豁免而是 Setter，报告必须保留区别。
- 同一函数或其所属类同时出现互相冲突的 NLT 与 `[LogTrack]` 时，正式分析失败并指出冲突位置，不猜测哪一个优先。

现有标签不作为真实行为分析的答案。第六模块复用原调用关系与修改判断，独立求取标签生效后的追踪结果；不另建图，不复用第一遍 Setter 的冻结证据。真实写入证据和追踪证据分别保存。中途报告只列已知事实，受豁免影响但尚未检查的追踪决定明确等待，不能生成补丁；最终报告重新检查，不继承等待状态。

## 四、统计范围

“可报告函数”指进入最终数量统计和标签差异的函数，包括：

- 普通命名函数。
- 运算符和类型转换函数。
- 属性 setter。
- 自定义事件 add/remove。
- 类级 NLT 下原本可报告的上述函数。

构造函数、析构函数、属性 getter、接口或抽象声明、没有函数体的 `extern` 声明、局部函数、匿名函数、编译器生成函数、`getInstance` 和 `BaseProxy_*` 不进入标签统计，但仍参与调用分析。按实际日志注入器共同规则，真实命名空间为 `Tss`、`UnityEngine` 或 `UnityEngine` 子命名空间的函数也不提标签建议；不把 `Tss.Child` 或其他命名空间中的同名类型误排除。类级 NLT 的独立复查要求不因此取消。

当前 khengine 中，程序集声明 `includePlatforms` 仅为 `Editor` 的源码程序集不进入日志标签统计，但源码、内存编译结果和依赖调用仍保留。依据：普通日志注入器默认只处理 `khengine.define`、`khengine.runtime`；Vulcan 读取 Player 程序集列表。当前 `khengine.editor.asmdef` 明确只支持 Editor，已有源码/DLL调用和格式错误回归，限域审计通过。这不是把编译输入改为 Player，也不声称已经实现任意 Unity 平台组合筛选。

## 五、七个模块

生产代码按以下七个模块组织，一个模块一份主文件。主文件可以包含本模块紧密相关的小类型，不再按类拆文件。

### 1. `MaterialLoader.cs`：找齐材料

- 找到 `khengine.runtime.asmdef` 当前唯一的 Unity 编译参数文件。
- Unity 保留多次构建材料时，读取 `Library/Bee/tundra.log.json` 首行明确记录的脚本构建图，验证图和对应响应文件存在；不按时间或目录名猜选。构建记录无效则停止，没有记录且多份候选也停止。
- 读取实际源码、条件编译标记、分析器引用、源码依赖和外部编译文件。
- 读取同一次 Unity 构建图明确列出的全部 C# 源码程序集及其引用，但只有 khengine 进入最终统计。只沿 khengine 的依赖方向会漏掉 Assets 提供的接口实现和回调；只连源码产物也会漏掉共享预编译 DLL 的消费者。因此不在材料阶段猜哪些程序集不相关，后续按真实调用读取必要函数体。
- 源码身份只接受当前构建图的真实产物到编译参数文件的对应；响应文件实际输出必须与其构建节点一致。邻近存在旧参数文件不代表它参与当前编译，不能据此把图外 DLL 当作源码重新编译。
- 保留 Unity 响应文件中的完整编译选项、分析器和源码生成器；生成的源码与普通源码一起进入材料。
- 保留响应文件的源码顺序，在内存中建立当前编译上下文，不读取或覆盖磁盘上的 Unity 输出；可报告程序集立即生成完整内容，外部程序集在函数或完整候选查询需要时生成。编译准备与完整内容生成耗时分别列出并计入实际阶段时间。
- 源码依赖按依赖顺序建立编译上下文，互不依赖的程序集并行；上层引用本轮依赖的编译上下文，不必先生成依赖文件，也不能用同名旧参考文件的成员表代替当前源码。源码新增或删除成员均进入本轮绑定。请求取消后整份材料失效，新请求可复用有效编译上下文，但不能继承旧材料的失败延迟任务。
- 参考文件以及类型转交目标映射到同一 Unity/.NET 环境中的真实承载文件；普通间接依赖先进入候选表，实际命中时按已核实的宿主装载规则查找，不用编译引用的版本替代运行事实。
- 先按当前 Unity 运行目录与已证明的程序集身份规则选择真实载体，参考文件即便只有类型转交记录也不能绕过这一步。参考文件继续供编译器使用，不与已选定的真实载体并列成两个运行分支。若真实载体自身继续转交，则沿它的真实记录查找。
- 只有完全没有同名运行载体的纯参考门面才保留为查找类型终点的别名材料，不贡献函数实现。普通参考文件缺少实现、身份不符或有多个实际载体仍明确失败；不能从编译参考补出真实运行库没有的行为。当前 Unity 编辑器的运行目录由实际编译配置与编辑器日志核实。
- 转交表中能唯一定位的载体继续进入候选范围；尚未使用且没有载体的转交记录保留，实际调用、继承或接口命中该类型时才强制查齐。不能因为参考门面还列有从未用到的类型，就读取其他平台或无关工具目录来补齐。多个合法载体、已登记的循环或身份冲突仍明确失败。
- 找不到、找到多份或身份不一致时直接失败并列出证据。

当前 Unity 2021.3.16f1_0 编辑器已核实使用非严格 Mono 装载：探测按实际文件名，显式运行引用另有元数据名称入口，版本、公钥不单独排除候选。参考根和 `.ref.dll` 不获得预载身份；源码程序集也参与同名竞争。材料、类型转交和函数目录共用同一来源索引，实际需要的多个载体明确失败，尚未使用的竞争不作全局选择。已删除不同代 IL2CPP Mono 源码中的旧框架版本表。当前运行目录没有重复文件名；若将来同运行目录出现该情况，材料仍明确失败，此项尚未改为按需失败。

### 2. `MethodCatalog.cs`：建立函数总表

- 源码内存产物与外部托管文件共用一套类型、参数、泛型和继承事实读取。Roslyn 与 Cecil 用标准文档成员编号配对；只在文档显示副本中去掉源码编号没有的编译修饰符，并补齐嵌套泛型显示结构，不改真实元数据或函数身份。源码只回贴位置、显示名、标签和统计范围，不能猜配对。
- 为每个源码命名函数保留逻辑身份；外部及编译器生成函数以“真实文件 + 元数据标记”天然唯一，在实际调用或候选类型需要时读取并在本次运行内保存，避免启动时创建几十万个无关对象。
- 记录类、函数、参数、文件、行号、标签和是否进入最终统计。
- 初始源码函数表仅收集可报告程序集，外部源码与 DLL 在实际类型或函数命中时进入同一目录，保留真实虚函数标记、参数和元数据位置。完整继承、接口候选查询目前仍需生成剩余源码程序集，包含集合表达式、迭代器及匿名委托等编译器生成类型；不能用源代码语法名单猜测哪些程序集可以跳过。重写与接口目标只在第四模块按当前类型实参求取，不重复保存 RelatedMethodIds 快照。外部候选类型一旦被命中，就从同一真实文件读取该类型的函数和方法实现表。没有生产读取者的额外名称、身份和反向关系表不预建；反射候选必须包含实际按需载入的 DLL 函数。

### 3. `BehaviorReader.cs`：读取函数行为

- 源码先由 C# 编译器转换成当前内存中的函数内容；源码位置、标签和可报告函数身份仍由源码目录保留。
- 当前源码的内存编译结果和真实托管动态链接库共用一套函数指令读取，不保留第二套源码行为分支或回退路径。
- 统一记录字段写入、属性写入、数组或集合写入、事件修改、`ref/out` 修改、调用、对象创建、返回、保存、注册、传出和对象来源。
- 每次普通变量读取都保留独立快照、所在基本块和执行顺序；赋值、调用、写入、返回使用同一套位置。变量的稳定存储身份只用于取地址、引用传参和闭包捕获。保留编译器给出的分支、异常处理和最终释放关系，不能只记源码行号或合并所有历史赋值。
- 这一模块只描述事实，不直接给出 Getter、Setter 或标签结论。
- 正式运行先读取 khengine 可报告函数，依赖函数体在模块 4 找到实际目标后补读；所需类型和函数由第二模块提供，不强制提前生成所有外部源码产物。
- 迭代器按编译器实际生成的创建函数与遍历函数分别读取；创建时不执行遍历函数，不手写第二套状态机或捕获规则。编译器生成函数参与调用分析，但不进入标签统计。

### 4. `CallTargetResolver.cs`：找齐调用目标

- 依据第三模块保留的执行关系，统一计算每个使用位置真正能到达的值来源；委托、反射与第五模块共用这份结果，不各自重复实现一套变量分析。
- 普通调用连接到明确函数。
- 接口调用连接到全部合法实现。
- 可重写函数连接到全部合法重写。
- 委托连接到全部可能绑定的函数。
- 事件回调与委托使用同一套绑定目标规则。
- 反射按类型、名称和参数解析字段、属性、函数与构造函数。
- `GetMethod("Foo")` 只匹配合法的 `Foo`；名称来自参数时追踪全部调用点传值。
- 反射名称允许由外部任意传入时，检查当前代码闭包内所有类型和签名能够匹配的成员。
- `FieldInfo.SetValue` 和 `PropertyInfo.SetValue` 产生普通写入关系，不硬编码最终结论。
- 每找到尚未读取的目标，就交给模块 3 补读，再继续解析它的调用；直到必要关系没有新目标。模块 4 与 5 联合验收，运行时共用已有调用和值来源。
- 普通调用迭代器函数只创建可遍历对象，只有实际遍历才连接其延迟函数体；不得在创建时直接传播函数体中的写入。

本模块按以下顺序实现和验证，不同时铺开多套算法：

1. 先准确接上普通调用和构造函数，复用函数总表中的身份与类型信息；每轮集中补读新命中的函数，已经读过的不重读。
2. 接上接口与可重写函数；候选表按真实继承、实现关系建立，不按函数名相似程度匹配。
3. 利用第三模块的执行顺序，计算一次变量在使用位置可能来自哪里。地址仍连接原变量，普通读取保留当时的值；这份结果供委托、反射与下一模块共同使用。
4. 接上委托、事件和反射；实际目标与实际接收对象、参数一起保存，不能只列出一个函数名而丢掉调用方式。
5. 没有新目标后固定结果顺序。保留全部参与分析的函数、已读行为、逐调用点的目标、共用值来源及耗时，不提前输出 Setter/Getter。

新写法加入本模块已有的目标读取或值来源处理，不新建插件、规则注册框架或按业务函数定制分支。每一步先做源码和真实 DLL 的对照测试，再用 khengine 检查实际调用。

2026-09-09 修正证明顺序：第四、第五模块共用已有调用关系和值来源。确定写入还必须有到达该位置的执行证明，不能把可能不返回的调用之后的写入当作既定事实，也不能从另一条分支借用对象来源。满足这些条件后，写入后面的独立未知调用不会推翻已经发生的修改。被调函数修改自身仍须按实际参数映射，不能直接复制给调用者。Setter 证明后继续保留标签审计和必要的待处理调用；Getter 必须闭合全部相关目标。相同且不影响判断的泛型实参应共享处理，但不同参数环境不能合并。当前只有专项测试和限域审计通过，不代表整个模块完成。

同日后续复现出四项整数条件误判：同值相减、按位与零、同一函数内互相矛盾的比较，以及跨函数传参后的矛盾比较。补充通用条件检查仍留在第四模块，不另建调用或变量分析图。使用统一版本的 Microsoft.Z3 4.12.2 表达 32/64 位整数运算，复用既有参数身份、赋值来源与前驱边；临时验证已确认本机装载及单线程配置正常。先验证排除不可能路径，再补齐写入对象与合法路径的联合证明；仅公式有解不能替代真实执行证明，未支持的循环、返回关联、异常或原生来源不能包装成任意整数。所有公式仅在一次冻结材料查询内有效，不建立跨轮缓存。此项进行中，不能继续声称“条件来源已闭合”等于“写入分支确实能执行”。

2026-09-07 根据用户要求自主决定：按被调用函数实际修改的对象向上传递影响。修改静态数据或调用者已有对象时传播；只修改调用者内部新建且没有传出的对象时不传播。参考 `Runtime/KFL/DSL/KFLCsLuaASTEncodeUtil.cs:135`：内部新建 `StringBuilder` 并调用 `Append`，最后返回字符串，拼接对象本身没有传出。仅这条拼接路径不能因为 `Append` 会修改自身，就判定上层修改了外部状态；其它调用仍独立检查。

### 5. `EffectAnalyzer.cs`：得出真实结论

- 先标出直接修改外部状态的函数。
- 再沿调用关系传播实际修改的对象和参数，逐调用点判断是否影响调用者外部状态。
- 跟踪新对象是否只在函数内部使用，还是被返回、保存、注册或传出。
- 循环调用使用同一轮稳定计算，不重复扫描全部函数。
- 全部关系闭合后，每个函数的真实行为只有 Getter 或 Setter 两种结论。

### 6. `AnnotationEvaluator.cs`：处理标签和差异

- 应用可信 NLT 与 `[LogTrack]` 规则；源码和 DLL 标签从同一份真实元数据读取。
- 仅对含可信豁免调用、真实为 Setter 且自身未豁免的入口复用第五模块，检查是否还存在需要追踪的修改；保持原业务程序集范围。真实行为不重新定义，调用和对象关系不重建。
- 生成可信豁免复查、裸 NLT 缺少 Reason 告警、上游调用过程和可补标清单。
- 只在这一模块决定标签规则，不改变前五个模块的真实行为分析；追踪未证明与真正的标签冲突分别报告。

### 7. `ReportWriter.cs`：生成交付结果

- 输出总函数数、检测结果数量和源码标签数量。
- 按类汇总两类主要差异。
- 输出可信豁免复查、缺少 Reason、失败证据和每阶段耗时。
- 已绑定原生调用也必须披露，不能因为入口已有独立 Setter 证据就从报告中消失。按根函数和目标分组，保留真实库/入口、运行时来源、调用绑定数，以及该根是否已有独立的真实结论和日志决定；只有后者可延期，未证明根不能标成无影响。已按真实语义处理的委托构造不列为未解决边界。
- 从同一结果生成文本、JSON 与补丁预览，顺序固定。

## 九、多线程和性能

命令行接受 `-j4`、`-j 4` 和 `--jobs 4`。数值是整个工具共用的最大并行工作数，不写死为 4。

默认工作数为 4，任意正整数有效，0 或负数直接拒绝。源码文件、外部文件、函数行为和动态目标等互不依赖的项目使用同一个并行上限。先找齐材料、建立目录，再由模块 3 与模块 4 补齐实际调用链，最后判断行为、处理标签和生成报告。

编译器内部并行统一关闭：当前编译器的内部队列没有按本工具的 `-j` 限额执行，不能仅凭“一份程序集”就放开。外层按 `-j` 同时编译独立程序集，每份完成后立即发布给后继，不等待整层全部完成。异常退出时收拢已经启动的工作，并保留原始失败。每一步结束后固定排序，因此 `-j1`、`-j2`、`-j4`、`-j8` 必须得到逐字一致的结果。

允许会话内复用编译上下文和持久化缓存。优先保存可核验的编译产物；源码、配置、引用、生成内容或工具版本改变后旧产物不能继续使用。分析结论另外依赖分析规则和完整关联输入，不能只凭 DLL 名称或日期复用。分别记录无缓存首次运行、进程重启复用、同会话未修改和编辑后更新耗时。完整分析目标是 5 秒以内，连同工具编译最低要求是 10 秒以内；每个模块单独计时。不同并行数的结论、证据、顺序必须一致，耗时与命中计数不要求逐字一致。

## 十、测试和自动审计

测试只通过模块公开结果或工具总入口验证行为，不检查内部拆了多少函数、调用了几次私有方法。每增加一种能力执行一次“先失败、再实现、再整理”的小循环。

同一个最小函数必须分别从源码和真实托管动态链接库读取，两种来源得到的写入、调用、创建、对象来源和最终真实行为必须一致。

全部代码组织、实现、测试编写与执行由主 Agent 负责；子 Agent 只做只读审计，审计打回的问题由主 Agent 修复，不把实现工作再分派出去。

每个模块必须经过：

1. 用明确预期的小例子覆盖正常情况和当前项目实际边界。
2. 编译、格式检查和全部自动化测试通过。
3. 在 KiHan 中只读查找本模块涉及的真实写法，并建立一一对应的最小测试。
4. 把代码、测试和本文件交给子 Agent 审计。
5. 审计不通过就自动修复并重新送审，直到明确通过；只有审计通过后才提交和推送。在已确认范围内自主判断并记录理由；只有需要额外授权或实质扩大范围时才询问用户。
6. 按最新要求先接通七个模块形成可运行版本，再依据真实报告逐项完善；模块 4 与 5 共用已有调用和值来源。等待审计期间继续独立检查和测试，不空等。
7. 通过后检查完整差异，提交并推送可回滚版本。

最终再用 `D:/KiHan/Packages/khengine/Runtime/khengine.runtime.asmdef` 完整运行：

- 每种真实写法都有对应测试。
- 托管分析没有未解决项；缺少外部材料的原生内部实现不再作为开发任务，单列仍受其影响的结论范围，不伪造 Getter/Setter。
