# SetterCheckerNew 设计与进度

## 一、最终目标

SetterCheckerNew 只服务于 `D:/KiHan/Packages/khengine`。

它读取 khengine 当前真正使用的 Unity 编译参数，直接检查源码和必要的真实托管 DLL，不为分析生成游戏程序集，最后回答：

1. 哪些可报告函数的真实行为是 Setter。
2. 哪些可报告函数的真实行为是 Getter。
3. 分析结论与源码现有标签有哪些差异。
4. 哪些人工豁免需要复查，哪些裸 `[NoLogTrack]` Setter 缺少 Reason。

工具生成文本报告、内容一致的 JSON 报告和标签修改预览，不自动修改 KiHan。

## 二、已经确认的判断规则

真实行为只分 Getter 与 Setter。以下行为属于 Setter：

- 实际修改当前对象、传入对象及其成员指向的对象、静态数据、集合、数组、事件或 `ref/out` 数据。
- 调用 Setter，且其修改对应到调用者的已有对象、参数或静态数据；不能把只修改内部临时对象的调用直接判为 Setter。
- 创建 khengine 业务对象并直接返回本身不算修改；写入已有对象、静态数据、参数，或将对象保存、注册、传给外部保存者，才算 Setter。

只修改函数内部创建且没有离开函数的临时对象，不属于 Setter。

只有函数自身及全部合法调用目标都没有对外部对象的修改，函数才是 Getter。不能判断的函数列出准确位置和原因，不猜成 Getter 或 Setter，不生成相应补丁，整轮验收不能视为通过。

`ShouldTrack`、`NoLogTrack` 和 `NLTClass` 是第六模块结合真实行为与源码标签后得出的最终日志决定，不是函数真实行为的别名。`[LogTrack]` 只强制最终决定为 `ShouldTrack`，不能把真实 Getter 改写成 Setter。

## 三、现有标签规则

- 方法级 `[NoLogTrack(Reason)]`、裸 `[NoLogTrack]` 和类级 `[NoLogTrack]` 都先作为可信人工豁免，最终不追踪。
- 工具仍独立检查所有豁免函数的真实行为。
- 类级豁免下的可报告函数标记为 `NLTClass`。
- 带 Reason 的 Setter 和类级豁免 Setter 进入“可信豁免复查”，不报警。
- 只有裸 `[NoLogTrack]` 被独立分析为 Setter 时，告警“缺少 Reason”。
- 该告警传到所有能调用它的上层可报告函数；每个函数只列一次最短调用过程。
- 没有 NLT、但实际是 Getter 的函数进入补标建议。
- 同一函数或其所属类同时出现互相冲突的 NLT 与 `[LogTrack]` 时，正式分析失败并指出冲突位置，不猜测哪一个优先。

现有标签不作为真实行为的答案。日志决定只看真实行为；可信豁免只决定函数自身不追踪，其内部写入照常使上层成为 Setter（用户 2026-09-24 确认）。

## 四、统计范围

“可报告函数”指进入最终数量统计和标签差异的函数，包括：

- 普通命名函数。
- 运算符和类型转换函数。
- 属性 setter。
- 自定义事件 add/remove。
- 类级 NLT 下原本可报告的上述函数。

构造、析构、属性 getter、接口或抽象声明、无函数体的外部声明、局部函数、匿名函数、编译器生成函数、`getInstance` 和 `BaseProxy_*` 不进入标签统计，但仍参与必要分析。具体统计与 khengine 当前日志注入规则一致；仅支持 Editor 的程序集不进入标签统计。

## 五、七个模块

生产代码按以下七个模块组织，一个模块一份主文件。主文件可以包含本模块紧密相关的小类型，不再按类拆文件。

### 1. `MaterialLoader.cs`：找齐材料

- 找到 `khengine.runtime.asmdef` 当前唯一的 Unity 编译参数文件。
- 读取实际源码、条件编译标记、分析器引用、源码依赖和外部编译文件。
- 源码项目直接互相引用，不先生成 DLL；外围材料用于查全声明和注册关系，命中函数后才读取其行为。只有 khengine 进入最终统计。
- 保留 Unity 响应文件中的完整编译选项、分析器和源码生成器；生成的源码与普通源码一起进入材料。
- 参考文件以及类型转交目标映射到同一 Unity/.NET 环境中的真实承载文件。
- 找不到、找到多份或身份不一致时直接失败并列出证据。

### 2. `MethodCatalog.cs`：建立函数总表

- 为源码和编译后文件中的每个函数建立唯一身份。
- 记录类、函数、参数、文件、行号、标签和是否进入最终统计。
- 预先建立类型继承、接口实现、函数重写和成员名称索引。

### 3. `BehaviorReader.cs`：读取函数行为

- 源码直接通过 C# 编译器读取函数操作，不生成内存或磁盘程序集。
- 真实托管动态链接库直接读取函数指令。
- 两者统一记录字段写入、属性写入、数组或集合写入、事件修改、`ref/out` 修改、调用、对象创建、返回、保存、注册、传出和对象来源。
- 每个函数体只提取一次事实，用一份修改说明保存写入对象、参数、返回来源等信息，不按调用链复制环境。
- 这一模块只描述事实，不直接给出 Getter、Setter 或标签结论。

### 4. `CallTargetResolver.cs`：找齐调用目标

- 普通调用直接查函数总表；以下目标以列表或字典保存并去重。
- 只保存固定调用处与实际参数的对应关系，不把函数沿调用路径反复展开。
- 接口调用连接到全部合法实现。
- 可重写函数连接到全部合法重写。
- 委托连接到全部可能绑定的函数。
- 事件回调与委托使用同一套绑定目标规则。
- 反射按类型、名称和参数解析字段、属性、函数与构造函数。
- `GetMethod("Foo")` 只匹配合法的 `Foo`；名称来自参数时追踪全部调用点传值。
- 反射名称允许由外部任意传入时，检查当前代码闭包内所有类型和签名能够匹配的成员。
- `FieldInfo.SetValue` 和 `PropertyInfo.SetValue` 产生普通写入关系，不硬编码最终结论。

### 5. `EffectAnalyzer.cs`：得出真实结论

- 先标出直接修改外部状态的函数。
- 再把“修改当前对象、静态数据、哪些参数”等说明对应到调用者；已有确定修改不反复证明。
- 说明有新增时只通知受影响的调用者，没有变化就不再处理，不因调用者不同重读函数体。
- 跟踪新对象是否只在函数内部使用，还是被返回、保存、注册或传出。
- 递归和互相调用在固定函数关系上传递新增说明，不展开调用路径、不重新扫描全部函数。
- 不把整条调用链的执行过程推算作为主干，不追加第二轮全量恢复；当前不能表达的写法单列后讨论。
- 全部关系闭合后，每个函数的真实行为只有 Getter 或 Setter 两种结论。

### 6. `AnnotationEvaluator.cs`：处理标签和差异

- 应用可信 NLT 与 `[LogTrack]` 规则。
- 生成可信豁免复查、裸 NLT 缺少 Reason 告警、上游调用过程和可补标清单。
- 只在这一模块处理标签，不改变前五个模块的真实行为分析。

### 7. `ReportWriter.cs`：生成交付结果

- 输出总函数数、检测结果数量和源码标签数量。
- 按类汇总两类主要差异。
- 输出可信豁免复查、缺少 Reason、失败证据和每阶段耗时。
- 从同一结果生成文本、JSON 与补丁预览，顺序固定。

## 七、外部代码与动态调用

- 使用当前 Unity 编译参数对应的真实源码和托管 DLL，不拿过期 DLL 冒充当前源码；声明查全与函数行为分析分开。
- 只分析会进入真机包的源码程序集；编辑器和测试程序集仅在被引用时参与编译，不作为实现或注册候选（用户 2026-09-24 确认）。
- 只有声明的参考文件必须映射到当前运行环境真实文件后再分析。
- 包装函数通过自己的源码或函数指令自然进入调用关系，不为 KFL、ReflectUtil 或具体业务函数写特例。
- 接口、重写、委托和反射统一遵守“全部合法目标都闭合”的规则。
- `Activator.CreateInstance` 解析传入类型及构造函数，并继续判断新对象是否离开函数。
- 第一轮不使用 LogicData 限制反射目标，不枚举未启用的条件编译组合。
- 不再索取缺失的原生材料，也不开发原生指令分析器。现有材料不能证明的影响明确单列，不能借此忽略托管分析缺陷。
- 运行时生成新代码或加载当前材料范围外的程序集，明确说明超出范围，不提供猜测结果。

## 八、禁止的实现方式

- 禁止按某个业务函数名、类名或报告差异硬编码 Getter、ShouldTrack 或忽略结论。
- 禁止 `Unresolved => ShouldTrack`、`Unresolved => NoLogTrack` 或任何保守兜底。
- 禁止捕获所有异常后继续分析、缺文件时扫描全盘、按相似文件名猜实现。
- 禁止为未出现的输入格式、旧版本、插件能力或跨运行缓存预建抽象。
- R2 懒加载与 R3 诊断边界是本轮已明确的例外：只按实际调用证据延迟读取初始化目标；仅保留能够说明分析范围、耗时和未覆盖原因的诊断数据，不恢复全局调用路径展开。
- 禁止为了“职责纯洁”把一段连续流程拆成大量只转发一次的小类。
- 必需的路径、文件、程序集身份和目标闭合校验不属于防御性编程，必须保留；禁止的是猜测、兜底和额外替代路径。

## 九、多线程和性能

命令行接受 `-j4`、`-j 4` 和 `--jobs 4`。数值是整个工具共用的最大并行工作数，不写死为 4。

默认工作数为 4，任意正整数有效，0 或负数直接拒绝。源码文件、外部文件、函数行为和动态目标等互不依赖的项目使用同一个并行上限。存在明确先后关系的七个模块按顺序执行。

各步骤共用并行额度，不叠加内部工作队列。结果固定排序，`-j1`、`-j2`、`-j4`、`-j8` 的结论和证据必须一致；耗时单独比较。多线程不能替代消除重复计算。

允许函数和类型字典、会话内源码上下文及有效持久化缓存；按当前源码、配置、引用和分析规则核验，不凭文件日期或同名 DLL 复用。

完整分析目标是 5 秒以内，10 秒以内勉强接受。工具构建、源码准备、缓存读取、分析和报告写出均计时，不能只报某个局部阶段。

每次主干改动都以真实 khengine 的完整运行时间和完整报告验收。当前批次自测后只运行一轮完整验收，不边跑边补特例、重复补扫；失败先汇报整体问题。源码程序集生成次数必须为零；每个函数体只提取一次事实，不因调用入口增多复制函数说明。

## 十、测试和验收

测试只通过模块公开结果或工具总入口验证行为，不检查内部拆了多少函数、调用了几次私有方法。每增加一种能力执行一次“先失败、再实现、再整理”的小循环。

同一个最小函数必须分别从源码和真实托管动态链接库读取，两种来源得到的写入、调用、创建、对象来源和最终真实行为必须一致。

每个模块必须经过：

1. 用明确预期的小例子覆盖正常情况和当前项目实际边界。
2. 编译、格式检查和全部自动化测试通过。
3. 在 KiHan 中只读查找本模块涉及的真实写法，并建立一一对应的最小测试。
4. 由主 Agent 亲自对照代码、测试和本文件审查，不再使用子 Agent。
5. 开工前说明模块方案并与用户讨论明确；需要新增判断规则或扩大范围时先讨论，不零散补特例。
6. 通过后检查完整差异，提交并推送可回滚版本。

真实验收固定使用 `D:/KiHan/Packages/khengine/Runtime/khengine.runtime.asmdef`，不只在开发最后才验证：

- 每种真实写法都有对应测试。
- 当前材料能够支持的托管分析必须完成；未覆盖项不能算作已完成或从统计中隐藏。
- 工具结论和源码标签的每项差异由主 Agent 复查归因，附文件位置、实现细节和判断原因。
- 用相同测试核对不同 `-j` 的结果一致性；完整 khengine 运行给出总耗时与报告，局部测试通过不代表验收通过。

### 执行规则

- 按表中顺序逐项实施，同时只改一个计算模块。开工先在会话说明具体改动；用户已授权本轮连续执行，本项有明确收益且正确性通过后继续下一项，无须重复请求相同方案授权。
- 不能以“写了索引”或“测试通过”代替性能通过，不能仅凭一次全程计时波动撤回方向。没有明显收益时，继续定位本项耗时和维护成本，精简或重构；算法不适用于实际输入时给出证据和替代设计，不静默跳过。
- 明显优化要求：同输入、同并行数、同缓存模式，本模块重复操作数明显减少，模块耗时下降超出对照波动，全程没有可归因的退化。只有理论改善而实际无收益，不勾选完成。
- 保留改前可执行文件和结果；先跑相关现有关键案例，再做 khengine 前后对照。必要时交错运行改前、改后排除机器波动，不并发运行分析。对比逐函数真实行为、日志决定、告警和未知原因，不只比较数量。
- 只保留一种实现：替换旧逻辑，不叠加通用通知框架、全局共享查询环境和无用缓存。Core 不超过 13,000 行，每个函数头部有简单用途注释。
- 全程按用户最新要求以约 15 秒为目标，包含材料、分析和报告写出，工具编译另计。现有未证明项不得删除或猜成结论，性能通过不能冒充整个工具功能验收通过。
